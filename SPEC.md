# GoodSentry

Status: design authorized by the user on 2026-10-14. Implementation is in progress; tasks/todo.md records verified increments and remaining acceptance work.

## Objective and acceptance boundary

Build an independently authored Go error tracking and observability server. Existing applications use their Sentry SDK by changing the DSN to GoodSentry. Deliver one application image containing the HTTP server, UI, background jobs, scheduler and migrations. PostgreSQL is the only required external service. Valkey is optional. Development and verification run in WSL2.

The user approved the capability map and authorized elaborating and executing its specifications, plans and tasks. The requested product name is GoodSentry. The existing workspace directory remains named SentryGo.

GlitchTip's publicly documented functionality is the minimum target, not merely an ingestion endpoint. Shipping an intermediate increment does not satisfy the complete goal. A capability is complete only when its observable result has been verified. Accepting and dropping an unsupported item is not functional compatibility.

## Clean-room method

Use public protocol specifications, product documentation, release notes, published API contracts and black-box SDK/CLI traffic. Do not read, copy, translate or adapt Sentry, Relay or GlitchTip server implementation source, tests, assets or database schema. Test SDKs as external clients. Keep provenance links here. Third-party Go libraries may implement general protocols such as PostgreSQL, compression and source maps.

## Architecture

Use one Go module, a small executable in cmd/goodsentry, net/http routing and explicit dependency construction. Embed static HTML, CSS and JavaScript using go:embed. The UI has no external CDN or runtime build service. Use pgx for PostgreSQL, migrations embedded with the binary, and transactions for consistency. Keep the database schema relational for memberships, keys and grouping; retain original structured event data in JSONB.

Ingest events durably before returning success. A request may normalize synchronously and commit the event and its alert work atomically. Postgres owns jobs and retry state. Acknowledged events must survive restarts. A unique project/event-id constraint prevents SDK retries from incrementing counts twice. Concurrent grouping uses a unique project/fingerprint constraint and database atomic operations. Claim background work with row locking and recover expired leases. Never require Redis for correctness.

HTTP, workers and scheduler stop on termination signals and close database connections. Startup applies forward-only, versioned migrations under a PostgreSQL advisory lock. Readiness checks the database. Deployment rollback requires a compatible binary or database backup restoration; destructive rollback migrations are not automatic.

Serve an original, responsive application UI with a compact sidebar, neutral surfaces, a teal accent, readable tables and accessible forms. The user authorized Tailwind/Tailwind UI on 2026-10-14; use Tailwind CSS compiled into the embedded static stylesheet. Build tooling is excluded from the runtime image. Show loading, empty, error and permission states. Preserve filters in URLs. Escape telemetry as text, including stack traces, tags and log bodies. Never render event content as trusted HTML.

## Deployment and configuration

Default HTTP port is 8000. docker compose up --build starts GoodSentry and PostgreSQL with health checks, persistent database storage and an uploads volume. The application image runs as a non-root user and includes CA roots. No separate web/worker/cron containers are needed. An externally managed PostgreSQL URL also works.

Canonical variables are DATABASE_URL, SECRET_KEY, GOODSENTRY_DOMAIN, PORT, EMAIL_URL, DEFAULT_FROM_EMAIL, VALKEY_URL and GOODSENTRY_ENABLE_* flags. Accept GLITCHTIP_DOMAIN and the supplied GLITCHTIP_ENABLE_LOGS/UPTIME/MCP/DUCKDB names as migration aliases, with explicit GoodSentry variables taking precedence. SERVER_ROLE=all_in_one is supported. Reject unsupported role values rather than silently losing background tasks. ENABLE_OPENAPI and ENABLE_ADMIN control GoodSentry's own API documentation and administration surface, not Django functionality.

An empty VALKEY_URL selects PostgreSQL-only operation. Optional features must report their actual availability. Never accept a true feature flag while leaving its behavior unimplemented. EMAIL_URL supports consolemail:// and SMTP, with credentials excluded from logs. Persist uploads under a configurable directory. Reject placeholder production secrets. Document local development defaults separately.

Memory target: measure application RSS under an explicit repeatable workload and publish results. The user's 256-512 MB example is an operational target, not a measured claim. Do not claim this target until a representative load test demonstrates it.

## Runtime and workspace contracts

Provide /healthz for process health and /readyz for database readiness. Setup creates the first account and organization without a shipped shared password. Accounts can log in/out and recover passwords when email is configured. Use a memory-hard or established adaptive password hash. Sessions are opaque random secrets, stored hashed, expire, and use HttpOnly/SameSite cookies with Secure under HTTPS. Browser mutations require same-origin/CSRF protection. API Bearer tokens are hashed, revocable and scoped to authorized organizations/projects. SDK ingestion keys identify a project and do not grant management access.

Organizations contain memberships and teams. Projects belong to an organization and may be assigned teams. The same identity can access multiple organizations only through membership. Enforce scope at every read and mutation. Owners/admins manage memberships, projects, credentials and alerts; members can perform the approved issue workflow. Do not expose a bootstrap endpoint after the first owner has been created. Record account, organization and project identifiers as opaque strings at the HTTP boundary.

## Ingestion contract

Support POST /api/{project}/store/ and /api/{project}/envelope/, including deployments under a URL path prefix. Parse Sentry protocol v7 authentication from X-Sentry-Auth, query parameters and the envelope dsn header. Multiple supplied identities must agree and match the route's project. An absent or invalid SDK key returns 403. Never use management tokens as SDK credentials.

Envelope headers and item headers are one-line UTF-8 JSON. Item length counts bytes and permits arbitrary binary data and internal newlines. Missing length consumes one line. An optional terminal newline, zero-length attachments, unknown attributes and unknown item types must not corrupt subsequent items. Reject malformed/truncated framing and negative/overflowing lengths. Preserve unsupported item metadata and account for unsupported types without pretending to provide their feature.

Accept identity, gzip, zlib-wrapped deflate, Brotli and Zstandard HTTP bodies. Support legacy store zlib+base64 encoding without Content-Encoding. Apply compressed and decompressed byte limits and bounded item counts. Return 413 on limits, 400 on malformed data, 415 on unsupported encodings and 503 on unavailable durable storage. Successful event submission returns 200 JSON with its event id. Return rate limits using 429, Retry-After and X-Sentry-Rate-Limits. Browser SDK requests support the documented simple content types and OPTIONS/CORS, with rate-limit headers exposed.

Persist errors/messages with timestamps, exception chains, stack frames, breadcrumbs, tags, users, request, contexts, SDK, environment, release and arbitrary extra fields. Store binary attachments associated with event IDs using generated paths; never trust client filenames as paths. Protect attachment reads with project authorization.

## Issues and artifacts

Default grouping is an independently designed stable hash of exception type and normalized stack location, with message fallback. Respect SDK custom fingerprint arrays and the {{ default }} marker. Grouping is project-scoped and deterministic. Repeated events update first/last seen and occurrence counts once. A new event for a resolved issue creates a visible regression according to recorded resolution state. Support unresolved/resolved/ignored, assignment, comments, search by text/status/environment/release/tags and sorting with pagination.

Merge groups without losing events or their original grouping keys; subsequent events follow the merged association. Unmerge restores the original partition. Retain activity history. Release operations support create/finalize/list/delete, commit metadata and deploys. Traditional source maps and debug-ID artifacts must turn a known minified JavaScript frame into its original file, line, column and source context. Upload acceptance alone is insufficient. Native minidumps and debug symbol formats require explicit upload and symbolication proof. Modern sentry-cli artifact bundles need their own verified compatibility contract.

The observed sentry-cli 3.8.0 artifact flow negotiates chunk parameters at `/api/0/organizations/{org}/chunk-upload/`, submits SHA-1 checksum/chunk order/projects and optional version/dist to `/artifactbundle/assemble/`, uploads missing chunks as multipart `file` (or negotiated `file_gzip`) and repeats assembly. Our decoder accepts the observed `SYSB` little-endian version 2 prefix and ZIP archive with `manifest.json`. Manifest file entries own their URL, type and debug-id headers; the bundle-level debug_id is not the source-file debug ID. Parse in memory without extracting client paths, reject duplicate/absolute/traversal member names and missing referenced members, and bound compressed input, individual members, total expanded bytes and entry counts. Unknown manifest metadata is tolerated. This decoder alone does not establish upload API or symbolication completion.

The first artifact integration stores validated JavaScript source maps by project, artifact URL, release, distribution and normalized optional debug ID. Artifact URL is metadata, never a filesystem path or fetch target. Owners/admins upload maps and organization members may list their metadata through authenticated native `GET/POST /api/v1/organizations/{org}/projects/{project}/sourcemaps`; POST is multipart with `file`, `name`, `release`, `dist`, `debugId`. A release or debug ID is required so maps from unrelated builds cannot silently apply. Identical upload retries are idempotent. Distinct content for the same project/name/release/dist/debug ID returns conflict; remove/replace semantics need an explicit later operation. During ingestion load maps scoped to the event's project and either exact debug ID or exact release/dist, then symbolicate before normalization/grouping and durable acknowledgement. Bound each selected map set to 100 maps and MAX_BODY_BYTES total data; return 413 when that processing budget is exceeded. Preserve original raw stacks. Only uploaded sources are used. Legacy events with no release/debug identity remain unchanged. Verify an actual HTTP upload followed by SDK-shaped capture and authenticated retrieval of original source location/context. Compatible release and CLI upload APIs and their UI remain separate pending acceptance work.

Projects show a source-map disclosure with metadata list and an owner/admin multipart upload form for artifact name, release, optional distribution/debug ID and the map file. Explain the release/debug-ID requirement, retain useful input on errors, distinguish new uploads from identical retries, and show the mapped stack through the existing issue detail. A member can inspect metadata without being offered write controls. Browser acceptance uploads its own synthetic map, captures a minified error and verifies the mapped file/line/source context at mobile and desktop widths.

Integration review reproduced two source-map defects that must be repaired before acceptance: a general third-party consumer accepts out-of-range source indices and panics on lookup, and its one-field unmapped segments retain a previous source. Use an independently authored bounded ECMA-426 v3 consumer for uploaded maps, validating VLQ/index/position semantics, indexed-section offsets and recursion; unmapped segments leave frames unchanged. Limit each parsed map and each selected set to one million mappings and nesting to 32. Preserve existing verified source URL/context behavior. Maps selected only through an event debug ID are eligible only for that frame's matching debug image; release/dist-qualified maps may also use URL matching. These rules prevent an unrelated frame from borrowing another build's artifact.

Source content follows the selected mapping's source record, including indexed sections whose source URLs happen to be identical but contain different text. Treat an empty sourceRoot as absent for existing v3 compatibility. These are explicit consumer decisions; map input and content remain independently authored from the public standard.

Uptime monitors support HEAD, GET, POST with expected status, TCP and heartbeat intervals. Store checks, response times and up/down transitions. Scheduler coordination prevents duplicate checks across application replicas; missed heartbeats become down and a subsequent heartbeat recovers. Configured monitor targets are the approved network boundary; bound timeouts, response reads and redirect behavior.

The first uptime slice uses native organization-scoped `/api/v1/organizations/{org}/monitors` GET/POST and `/{monitor}` GET/PUT/DELETE, with `/{monitor}/checks` GET. Members read; owners/admins create, replace configuration, pause/resume and delete. An optional project slug must belong to that organization. JSON configuration contains `name`, `type` (`HEAD`, `GET`, `POST`, `TCP`, `heartbeat`), `url`, `project`, `intervalSeconds`, `timeoutSeconds`, `expectedStatus`, `expectedBody`, `confirmationThreshold`, `enabled`. Defaults are enabled, 60 seconds, 20 seconds, status 200 and threshold 1. Validate intervals 1..86400, timeouts 1..60, thresholds 1..100, HTTP status 100..599, name 1..200 Unicode characters, URL at most 2000 and expected body at most 2000. Type cannot change after creation. TCP targets use host:port with bracketed IPv6. Heartbeat targets have an empty URL. HTTP permits absolute HTTP/HTTPS URLs without credentials or fragments; HEAD/POST send no payload. A nonempty expected body on GET/POST means a literal substring within the first 1 MiB, an independent GoodSentry decision because the public contract does not define matching. HEAD/TCP/heartbeat reject expected-body configuration. No custom headers or target authentication are claimed by this slice.

Use UTC PostgreSQL `timestamptz` instants with microsecond precision for creation, deadlines, claims and recorded checks. JSON emits RFC3339 instants. Intervals are elapsed seconds, not civil-time schedules; no daylight-saving recurrence applies. The database clock owns eligibility, leases, heartbeat receipt and completion. A network result records elapsed milliseconds using Go's monotonic clock. The next network deadline is completion plus interval, so a slow check does not create a catch-up burst. A new or resumed heartbeat deadline is database now plus interval. A heartbeat arriving strictly before or after its deadline records an up check and resets the deadline; expiry is eligible at equality. No additional grace interval is assumed. Missed-heartbeat checks recur at the configured interval until recovery and participate in the same consecutive-failure threshold.

Persist monitor configuration/current state and append-only check history, including raw up/down result, confirmed status (`unknown`, `up`, `down`), previous status, transition flag, start/completion instants, optional HTTP status, response time and a bounded reason code. Consecutive failures change confirmed status to down only at the threshold; a successful check resets failures and recovers immediately. Initial status is unknown. Configuration changes clear failures, keep the last confirmed status, invalidate any in-flight lease and rearm the next deadline. Pausing preserves history/status and suppresses probes and heartbeat writes. Check history defaults to transitions and supports all checks with 25-row pages. Deletion removes its checks. Durable alert delivery remains a separate acceptance item.

Claim one due enabled monitor with `FOR UPDATE SKIP LOCKED`, assign a random fencing token and database lease of timeout plus 30 seconds, then release the transaction before network I/O. Two workers per process by default, configurable with `MONITOR_WORKERS` 1..16, share this PostgreSQL queue across replicas. Completion locks the monitor and accepts only its current unexpired token; pause/update/delete or a fresh heartbeat invalidates old work. Expired leases are reclaimable after restart. This prevents concurrent valid check completions, not exactly-once external network requests after a crash. Cancel workers on shutdown before closing PostgreSQL, and do not record cancellation as a service outage. Log scheduler claim/storage failures with stable operation and monitor identifiers, excluding target URLs, heartbeat tokens and credentials.

An opaque random 128-bit heartbeat capability is exposed as `heartbeatURL` only through authenticated monitor reads. `POST /api/v1/heartbeat/{key}` records a check without a management session and returns the check; GET is not supported. Ignore a body up to 1024 bytes and reject larger bodies with 413 before writing a check. It grants no management access. Serialize heartbeat receipt and completion on the same monitor row so a stale expiry cannot overwrite a fresh heartbeat.

Block private, loopback, link-local, unspecified and multicast destinations by default. `GOODSENTRY_UPTIME_ALLOW_PRIVATE_IPS=true`, with `GLITCHTIP_UPTIME_ALLOW_PRIVATE_IPS` as its migration alias, explicitly permits internal targets. Resolve and validate every address at connection time, connect to a validated address, apply the same rule to every redirect, disable environment proxies, verify HTTPS certificates, limit redirects to five and bound the whole probe by its timeout. Read at most 1 MiB plus one byte for body matching and bound response headers. Public configuration validation does not perform network requests. Feature flags remove uptime routes/UI and suppress workers when false. Add uptime availability to the authenticated session feature object.

The Tailwind UI lists monitor status, target, interval and last check, provides accessible owner/admin creation and edit/pause/delete controls, and shows monitor detail with transition/all-check pagination and a copyable heartbeat URL. Member views omit write controls. Preserve useful fields after validation/storage errors. Verify HTTP/TCP down/recovery, heartbeat expiry/recovery, pause, threshold, cross-organization isolation, concurrent claims, stale completions and expired-lease recovery against real PostgreSQL, plus the actual responsive browser workflow. SSL certificate monitors appear in the current public schema and remain a separately tracked parity requirement until their behavior is researched and verified.

Alert rules use error counts over a rolling window and notify on threshold crossing with cooldown. Uptime transitions trigger down/recovery messages. Persist deliveries, retry failures with bounded backoff and expose delivery status. Email and webhook payloads contain a link to the actual issue/monitor. Do not claim exactly-once external delivery; persisted intents provide at-least-once delivery with stable delivery identifiers.

Frequency means all non-transaction issue events in the project, including message events, filtered by configured environments. Use PostgreSQL `events.created_at` receipt instants, change its default to `clock_timestamp()` for new inserts and index project/receipt time. Do not reinterpret historical receipt timestamps. In the ingestion transaction, after duplicate suppression/event insertion and before commit, lock matching rules in increasing ID order. A new event triggers only if it lies in `(database now - window, database now]`, the count excluding that event is quantity minus one, and cooldown since the last trigger has elapsed. Count queries may stop at quantity. No repeat fires while the count remains above threshold, and a crossing suppressed by cooldown does not become a delayed alert. Evaluate future events only, without retrospective sends when a rule is created or edited. Preserve the existing advisory-identity/issue lock order before rule locks.
