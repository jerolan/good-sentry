## Objective and acceptance boundary

Build an independently authored Go error tracking and observability server. Existing applications use their Sentry SDK by changing the DSN to GoodSentry. Deliver one application image containing the HTTP server, UI, background jobs, scheduler and migrations. PostgreSQL is the only required external service. Valkey is optional. Development and verification run in WSL2.

The user approved the capability map and authorized elaborating and executing its specifications, plans and tasks. The requested product name is GoodSentry. The existing workspace directory remains named SentryGo.

GlitchTip's publicly documented functionality is the minimum target, not merely an ingestion endpoint. Shipping an intermediate increment does not satisfy the complete goal. A capability is complete only when its observable result has been verified. Accepting and dropping an unsupported item is not functional compatibility.

Use public protocol specifications, product documentation, release notes, published API contracts and black-box SDK/CLI traffic. ## Architecture

Use one Go module, a small executable in cmd/goodsentry, net/http routing and explicit dependency construction. Embed static HTML, CSS and JavaScript using go:embed. The UI has no external CDN or runtime build service. Use pgx for PostgreSQL, migrations embedded with the binary, and transactions for consistency. Keep the database schema relational for memberships, keys and grouping; retain original structured event data in JSONB.

Ingest events durably before returning success. A request may normalize synchronously and commit the event and its alert work atomically. Postgres owns jobs and retry state. Acknowledged events must survive restarts. A unique project/event-id constraint prevents SDK retries from incrementing counts twice. Concurrent grouping uses a unique project/fingerprint constraint and database atomic operations. Claim background work with row locking and recover expired leases. Never require Redis for correctness.

HTTP, workers and scheduler stop on termination signals and close database connections. Startup applies forward-only, versioned migrations under a PostgreSQL advisory lock. Readiness checks the database. Deployment rollback requires a compatible binary or database backup restoration; destructive rollback migrations are not automatic.

Serve an original, responsive application UI with a compact sidebar, neutral surfaces, a teal accent, readable tables and accessible forms. The user authorized Tailwind/Tailwind UI on 2026-10-14; use Tailwind CSS compiled into the embedded static stylesheet. Build tooling is excluded from the runtime image. Show loading, empty, error and permission states. Preserve filters in URLs. Escape telemetry as text, including stack traces, tags and log bodies. Never render event content as trusted HTML.

### Account credential generations and authenticated password changes

This workspace increment supplies the shared revocation contract needed by password recovery. It also lets any signed-in owner, admin or member change their own password without an email service. Email recovery, invitations, team and membership management remain required capabilities with separate delivery and authorization contracts. This section defines GoodSentry's native behavior independently; no external account API equivalence is claimed.

| Workspace child | Consumer and acceptance boundary | Dependency |
|---|---|---|
| credential-generation | Login/bootstrap session issuance and native API-token issuance retain their original authentication generation; password changes atomically invalidate all of that user's credentials | Existing accounts, sessions and scoped API tokens |
| account-password | A signed-in user changes their own password through API and original Account UI, then signs in again | credential-generation |
| account-mail | Purpose-specific account messages, secret handling and actual SMTP delivery/retry behavior | Existing mail transport; its alert payload and project-required outbox are insufficient |
| account-recovery | Email request and single-use redemption with enumeration, expiry, replay and generation rules | credential-generation, account-mail |
| membership-invitations | Owner/admin membership and team management, invitation issuance and acceptance for new/existing identities | account-mail; complete role/last-owner and invitation contracts still required |

Additive migration035 after034 adds `users.auth_generation bigint NOT NULL DEFAULT 1 CHECK (auth_generation > 0)`. Preserve every existing password hash, user identifier, session, token, grant, membership and migration receipt. Do not rewrite credentials during the upgrade. Carry `AuthGeneration` in the internal `User` returned by bootstrap, email lookup and session admission; exclude it from JSON just like `PasswordHash`, including nested comment/activity users. A zero/missing generation never authorizes credential issuance. Existing session and token rows need no generation column under the locking contract below.

Both production issuers must require the generation observed by their caller. Login retains the generation from the same user lookup whose password hash passed bcrypt; bootstrap retains the inserted generation. Native API-token creation retains the generation from the session middleware's original admission. Never refresh that value after a mismatch or retry using the previous password/session proof. Require it in the store interfaces; leave no overload/default that issues credentials using user ID alone. All future credential issuers and password-reset authorizations must obey this rule too.

Session and API-token issuance use an explicit `pgx.ReadCommitted` transaction. Lock the user's row `FOR SHARE`, compare its generation with the observed value, and retain the lock through credential commit. API-token creation then keeps its current membership SHARE and sorted selected-project SHARE locks and authorization checks. Credential issuance orders its locks as user, membership, selected projects, credential. This is a requirement for these issuers, not a claim that every existing issue workflow takes user locks first. A missing or changed user fails with a dedicated internal credentials-changed error and no inserted credential. Preserve existing project-scope, role, expiry, one-time-secret and CSRF behavior.

Password change uses explicit `pgx.ReadCommitted` regardless of the deployment's default isolation. Lock the user's row `FOR UPDATE` before any password or credential mutation; compare the original authentication generation. In that same transaction replace the password hash, increment the generation once, delete all sessions belonging to the user, and revoke all their unrevoked personal API tokens across every organization. Use `api_tokens.user_id`, without an organization filter; expired unrevoked tokens are included. Preserve existing `revoked_at` values and all token/grant history. Capture one database timestamp after acquiring the user lock for the newly revoked rows. Other users' credentials, memberships, project keys/DSNs and retained telemetry remain unchanged. An exhausted bigint generation or a confirmed transaction abort changes none of the state; never wrap or reset the counter. If the connection fails during COMMIT, the whole operation may have committed even though the client receives an error. A deferred rollback cannot remove that uncertainty. Do not automatically retry or claim the password stayed unchanged; verify the result through a new sign-in.

When issuance acquires its user SHARE lock first, password change waits, then its subsequent credential statements see and invalidate that committed credential. When password change wins first, waiting issuance observes the new generation and fails. Two changes with the same original generation have one winner. Ordinary requests admitted before revocation keep the existing in-flight-request semantics; they cannot use that admission to issue a fresh credential after the generation changes. Later authentication rejects deleted sessions and revoked bearer tokens. A login with the new password reads the new generation and can issue a usable session.

The need for a fresh statement snapshot follows PostgreSQL's [Read Committed and Repeatable Read contracts](https://www.postgresql.org/docs/18/transaction-iso.html). Repeatable Read can retain a snapshot taken while an issuer holds a lock and subsequently miss the issuer's committed credential. User SHARE must conflict with the exclusive password-change lock, as specified by PostgreSQL's [row-lock modes](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS). This reasoning requires real interleaving tests before acceptance; documentation review is not a concurrency proof.

Register prefix-aware `POST /api/v1/account/password` through the existing native session/CSRF/same-origin middleware. Bearer or DSN credentials alone never authorize this route. Preserve native cookie handling when an Authorization header is also supplied; only compatible routes apply bearer precedence. The body is one JSON object with required string `currentPassword` and `newPassword`; reject unknown fields, invalid types, trailing JSON and bodies beyond the existing1MiB native limit. The current password is1..72 bytes and the new password12..72 UTF-8 bytes. Do not trim either password or substitute character counts for byte bounds. Reusing the same password is permitted and still performs the full revocation operation.

Load the user's current password hash and generation by the admitted user ID. Reject a generation mismatch with401 before treating that newer hash as authorization for the old session. Compare the current password with bcrypt, then compute the replacement bcrypt hash outside the write transaction, using the existing adaptive cost. Pass the original admitted generation into the store mutation. Malformed input or an incorrect current password returns400 and changes no account or credential state. A stale/removed identity returns401 and issues no cookie. Invalid/missing session and CSRF/origin failures retain401/403. Storage failure returns503 with the existing generic response and no hash, password or generation disclosure. Login whose generation loses a race returns its existing generic401 credentials failure; native token creation returns401 for that stale session. Do not translate this condition into a misleading resource-conflict response.

Return204 only after the password transaction commits. Expire the current session cookie with the existing prefix, HttpOnly, SameSite and HTTPS Secure attributes, and require a new sign-in; do not automatically issue a replacement credential. Passwords, hashes and authentication generations never enter response bodies, URLs, telemetry or logs. If the client loses the response after commit, it can sign in with the new password. Do not promise an HTTP retry using the revoked session will succeed.

Expose an Account link beside the signed-in identity and sign-out action, using the existing `view=account` navigation. It is available to every authenticated role and to an identity with no current organization; render it before organization/project loading. Show the account's name/email as text and a labeled current/new/confirm password form with `autocomplete=current-password` and `new-password`. Explain before submission that a successful change signs out every session and revokes personal API tokens in every organization, while project SDK keys keep working. Confirmation is a browser check; do not add it to the API contract. Disable duplicate submission while pending. Show safe, accessible validation/server feedback without persisting any password beyond the mounted form. Clear fields when leaving the view or receiving an authentication failure; never retain them in shared state, history or browser storage. On success clear authenticated application state and show the sign-in form with a plain success message. A400 leaves the form available without claiming completion. A503 or failed network response leaves it available but explains that the result could not be confirmed and offers a new sign-in to verify it; do not resubmit automatically. The usual keyboard, focus, responsive and safe-text rules apply.

Real PostgreSQL owns035 upgrade preservation/reopen, explicit-isolation behavior, generation checks, all-user-session removal, cross-organization token revocation, unchanged already-revoked timestamps and unrelated-user/project-key preservation. Extend existing session/token fixtures and use real transactions to observe blocking before release, with bounded cancellation and existing database observation helpers. Avoid sleeps as synchronization and production-only test hooks. ### Account email and single-use password recovery

Account mail is purpose-specific and independent of project alert mail. Reserve additive migration036 after035 for `account_password_resets`: a text delivery ID, owning user, recipient, unique64-hex token hash, AES-GCM token ciphertext, issuing authentication generation, expiry, nullable consumption instant, delivery state (`pending`, `processing`, `sent`, `failed`, `consumed`, `canceled`), attempt count, next-attempt instant, creation/update/send instants, bounded reason, and fenced lease token/expiry under the same processing-state check used by alerts. Index due pending work and expired leases without rewriting existing rows.

`register` and `login` screens expose a password-reset request form. Request normalization lowercases and trims one email of at most254 bytes. Malformed bodies, unknown fields, invalid email syntax, unknown accounts and recently requested accounts return the same202 with no response data; known nonrate-limited accounts enqueue a reset in one Read Committed transaction. Require the generation from `UserByEmail`; lock the user FOR SHARE, reject a changed/missing generation, replace earlier unconsumed resets, and enforce a60-second per-user request floor. Do not disclose account existence through explicit status, response bodies, diagnostics or mail transport errors; this is not a constant-time timing promise. Every valid request returns202 only after its enqueue transaction commits; storage failure returns503. A recently requested account leaves existing pending mail/token unchanged. Creation accepts only the authenticated email; no caller-supplied destination.

A reset token is 32 random bytes as64 lowercase hex digits. Store only its HMAC-SHA256 under SECRET_KEY. Encrypt the raw token with AES-256-GCM derived from SECRET_KEY and bind the token hash as AAD; use a fresh random nonce and reject malformed, truncated, swapped or unauthenticated ciphertext. The encrypted token exists only in the dedicated outbox and is never returned, logged, shown in history or placed in application telemetry. A reset request is usable only after its delivery state is `sent`, its generation equals the current user generation, it is unconsumed and the database clock is before expiry. Links expire30 minutes after creation.

The one application worker sends a plain-text MIME message through the existing SMTP/consolemail transport with a stable delivery Message-ID and a link to the configured public domain/path prefix. The body contains the recipient's display name, exact expiry instant, single-use warning and instructions to ignore an unsolicited request. Use a fixed account-reset subject and no project payload/rules. Bound the generated URL and MIME body; reject unsafe recipient/header/URL input as permanent without SMTP. SMTP4xx, network/timeout/cancellation retry under the shared completion/fencing policy; SMTP5xx is permanent. Retry delay is the existing bounded alert backoff unless a future explicit provider minimum is implemented. Expired work becomes failed without sending. A new request can make an old emailed link unusable; delivery and reset are at-least-once, never claimed exactly-once.

Reset uses one explicit Read Committed transaction: read token owner without lock, lock the current user first FOR UPDATE, then lock and revalidate the reset row so a concurrent password mutation cannot authorize stale proof. Require current generation, sent/unconsumed/unexpired state and then replace the password, increment generation once, delete every session, revoke every unrevoked personal API token across organizations, mark the reset consumed and invalidate every other unconsumed reset for that user. A stale/expired/consumed/foreign/malformed token returns400 without writes; success returns204 and expires the current session cookie. The normal authenticated password change also invalidates every unconsumed reset.

The reset form consumes a `resetToken` query parameter without persisting it into application state or storage. It asks for new/confirm passwords, sends only the new password and token, prevents duplicate submissions, clears the URL token on success, and shows a generic sign-in result. Request success shows the same enumeration-safe message for every syntactically valid email. Invalid/expired links explain how to request another message. Recoverable storage/mail errors do not claim delivery. Keep keyboard focus, accessible feedback, safe text,320/768/1024/1440 layout and no password retention after leaving.

### Organization people and teams

Organization members and project teams are managed through the native authenticated API and a People view available to current owners and admins. Members may read organization membership and teams through the API; only owners/admins may mutate them. All mutations retain session/CSRF/same-origin controls. IDs are canonical positive numeric strings. Users from another organization and absent teams/members return404; malformed IDs, roles and names return400.

`GET /api/v1/organizations/{org}/members` returns `{data:[{id,name,email,role}]}` ordered case-insensitively by name then numeric ID. Owners set `owner`, `admin` or `member`; admins set `admin` or `member`, cannot promote to owner or mutate an existing owner. The organization row is locked before membership changes so concurrent operations serialize. The last current owner cannot be demoted or removed and returns409. Removing a member deletes that organization membership, team memberships in its teams and membership-owned tokens/assignments through existing foreign keys; it does not delete the user, sessions for other organizations or historical comments/activity.

`GET/POST /api/v1/organizations/{org}/teams` lists or creates teams; `GET/PATCH/DELETE /api/v1/organizations/{org}/teams/{team}` reads, renames or deletes one. Team names trim to1..120 Unicode characters without controls; slugs are generated once and immutable. Team records expose numeric string ID, slug, name, current member count and project count. Creation conflict is409. The bootstrap `default` team has slug immutable and cannot be deleted; its display name may change. Deleting another team removes its team memberships and sets owning project `team_id` to null while preserving project data. Team details expose ordered current organization memberships only.

`POST/DELETE /api/v1/organizations/{org}/teams/{team}/members/{member}` adds/removes an existing member of the same organization. Add is idempotent; remove is idempotent for an absent assignment. Both reject foreign users/teams. Team membership is display/grouping/alert metadata and does not widen project or event access. Every People mutation updates the view in place with recoverable validation errors; removal/deletion requires an explicit confirmation communicating token, assignment, team and project-association effects.

Pure/API checks own canonical IDs and strict bodies. Real PostgreSQL owns owner/admin permissions, last-owner races, serialized role/removal updates, membership cascades, team uniqueness, default-team protection, project unassignment and reopen persistence. Real HTTP owns session/CSRF separation and member/owner status codes. Browser acceptance covers role/team creation, add/remove, last-owner/conflict errors, confirmations, keyboard focus and responsive layouts. Copy-image/restart, full integration/race/vet and public CI remain required. Invitations and acceptance into a new account remain a separate required child; this management surface cannot create credentials or add an arbitrary email.

### Organization invitations

Additive migration037 after036 stores organization email invitations: delivery ID, organization, normalized email, role, inviter, unique token hash, encrypted token, creation/expiry/acceptance instants, delivery state/attempts/next attempt, bounded reason and the same fenced lease fields as account mail. Permit at most one active `pending`, `processing` or `sent` invitation for the same organization and case-insensitive email through a partial unique index. Seven-day expiry follows the database clock. Persist no raw token. The delivery worker uses a generic greeting when the invitee has no display name; a valid email address up to 254 bytes must not be constrained by the 120-character display-name limit.

Owners may invite `owner`, `admin` or `member`; admins may invite `admin` or `member`. The recipient must not already have an organization membership. Creation reuses session/CSRF, organization-row serialization, the accountmail AES-GCM/token-hash contract and SMTP/consolemail retry worker. Owners/admins list pending invitations and may cancel one; cancellation clears any lease and makes its emailed link unusable. Delivery retry success marks the invitation `sent`; permanent/expired delivery failure leaves it unusable and visible. Invitation acceptance validates state, expiry and current organization existence in one transaction, locks the organization and invitation, creates the user only when absent, verifies an existing user's email and credential generation, creates exactly one membership, and consumes the invitation. An existing account accepts with its password; a new account supplies name and a valid12..72-byte password. Success issues a normal session. ### MCP OAuth authorization prerequisite

When MCP is selected, provide a same-origin OAuth2 authorization server for MCP clients, based on the public MCP2026-07-28 authorization specification, RFC9728 protected-resource metadata, RFC8414 authorization-server metadata, RFC7591 dynamic client registration, RFC7636 PKCE and RFC8707 resource indicators. Do not copy Sentry/GlitchTip implementation code. This prerequisite implements OAuth authorization-server discovery; it does not claim OpenID Connect or issue ID tokens. MCP remains unavailable in the executable until this OAuth flow, forced-2FA/current-account checks, all17 tools and enabled-feature UI acceptance pass.

Public RFC9728/RFC8414 metadata endpoints are prefix-aware and no-store: `/.well-known/oauth-protected-resource`, `/.well-known/oauth-protected-resource/mcp` and `/.well-known/oauth-authorization-server`. They advertise the canonical resource `DOMAIN/PREFIX/mcp`, local issuer `DOMAIN/PREFIX`, authorization/token/registration/revocation endpoints, authorization-code+refresh grants, S256 PKCE, token response method POST and only enabled scopes: `org:read`, `project:read`, `event:read`, `event:write`, and, when logs are enabled, `log:read`. No implicit/password grant, client credentials, wildcard redirect URI, bearer query token or credentials in logs.

`POST /oauth/register` accepts a bounded JSON object: `client_name`1..100 valid characters, `redirect_uris`1..5 distinct absolute HTTPS URIs (HTTP allowed only for loopback `127.0.0.1`/`[::1]` with no fragment/userinfo), `token_endpoint_auth_method` exactly `none`, and `grant_types`/`response_types` omitted or exactly authorization_code/refresh_token and code. Generate an opaque public `client_id`; reject duplicate/unknown/null fields and excessive bodies. Registration never grants a user or token. Consent occurs separately.

`GET /oauth/authorize` validates response_type=code, registered client and exact redirect URI, state at most512 characters without controls, optional resource exactly equal to the canonical MCP URI, nonempty requested scopes that are enabled and supported, and PKCE S256 challenge of43..128 base64url characters. Invalid client/redirect fails locally without redirect; other validated request errors redirect to the exact client URI with code-less OAuth error/state and `iss`. An unauthenticated request renders a branded login form; POST `/oauth/login` authenticates against current users, enforces the current auth generation and creates the same secure session cookies, then redirects only to a relative validated authorization URL. An authenticated GET renders organization and project selection plus requested scopes without issuing a code.

`POST /oauth/authorize` requires the current session, same-origin form, session CSRF, and the same validated request. The user chooses exactly one current organization, either all of its projects or a nonempty subset, and explicitly approves the requested scopes. Denial redirects with `access_denied`. Approval atomically rechecks current membership, generation and project ownership and stores only a hash of a random single-use authorization code valid10 minutes. Response includes code, state, and `iss`. A code is bound to client/redirect URI/user/organization/project grant/scopes/PKCE challenge.

`POST /oauth/token` accepts form encoding. Authorization-code exchange requires exact client/redirect and a43..128 base64url verifier whose SHA-256 base64url value equals the stored challenge; expired/consumed/mismatched/replayed codes fail generically. It atomically consumes the code and issues a random one-hour native `gs_` Bearer token plus a thirty-day opaque refresh token, both stored as keyed hashes with the same organization/project/scopes. Response is JSON no-store with access_token, token_type Bearer, expires_in3600, refresh_token and scope. Refresh-token exchange requires client_id and, for public clients, rotates exactly once: revoke/link the predecessor and its prior access token, atomically issue a fresh access/refresh pair with the unchanged grant. Reuse, expiry, client mismatch and revoked grants fail generically. `POST /oauth/revoke` accepts form client_id/token and revokes matching access or refresh identity idempotently without revealing whether it existed.

All migrations preserve prior rows and constraints; existing token scopes/defaults remain unchanged.
