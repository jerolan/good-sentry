01 / ERROR TRACKING

See the signal, not just the exception.

Grouped issues keep stack traces, breadcrumbs, tags, affected users, comments and triage history together. Search and filters stay on durable event data.

  • Assign, resolve, ignore, merge and comment
  • Release and environment aware history
  • Exact event context and binary attachments
02 / DEBUG CONTEXT

Read the stack you actually shipped.

JavaScript source maps, debug IDs and native symbol files connect minified or compiled frames back to useful source locations without discarding the original event.

  • CLI and native source-map uploads
  • DWARF, dSYM and Breakpad symbolication
  • Raw JSON and attachment inspection
03 / PERFORMANCE

Follow the slow path across a trace.

Inspect transactions, standalone spans and child operations with latency percentiles, trace ancestry and cross-project waterfall views.

  • Average, p50 and p95 latency
  • Time windows and operation filters
  • Linked logs and related errors
04 / LOGS

Typed logs, without losing the edge cases.

Search retained Sentry and OpenTelemetry logs by service, level, environment, time or trace. Inspect attributes without rounding 64-bit integers.

  • OTLP/HTTP protobuf and JSON
  • Trace-correlated log inspection
  • Deduplication and bounded pagination
05 / UPTIME & ALERTS

Know when availability changes.

Schedule HTTP, TCP, SSL and heartbeat checks. Error-frequency and uptime rules deliver durable email, Slack, provider webhook or generic webhook attempts.

  • Failure thresholds and recovery history
  • Persistent delivery queues and retries
  • Provider-native alert payloads
06 / PEOPLE & ACCESS

Run the workspace close to the work.

Invite members, manage owners, admins and teams, scope API tokens, attach projects to multiple teams and verify secondary sign-in emails.

  • Owner last-guard and atomic owner transfer
  • Organization-contained project teams
  • Password recovery, instance and per-organization OIDC, email verification
07 / ACCOUNT SECURITY

Credentials you can operate yourself.

Change the password with global session and token revocation, recover access by email, add verified secondary sign-in addresses, require a TOTP code from your authenticator app and use OIDC when configured.

  • Single-use recovery and verification links
  • Optional TOTP two-factor sign-in with single-use recovery codes
  • Primary and verified secondary email addresses
  • Owner-controlled API tokens and permissions

MAKE IT YOURS

Bring Docker.
Keep your SDK.

Pull the public application image and start it alongside PostgreSQL. No separate web or worker services to assemble.

  1. 01

    Start the stack

    You need Git, Docker with Compose, and OpenSSL.

  2. 02

    Open your workspace

    Visit localhost:8000. The first start creates one owner and organization, so you land in the workspace; add a project and copy its DSN.

  3. 03

    Point your SDK at its DSN

    Copy the project DSN into your existing Sentry SDK configuration. Verify the capabilities your application needs.

TERMINAL / LOCAL SETUP
git clone https://github.com/jerolan/good-sentry.git
cd good-sentry
test -f .env || printf 'SECRET_KEY=%s\n' "$(openssl rand -hex 32)" > .env
docker compose up -d
↳

Keep your .env between restarts. The secret protects sessions. Local mode has no login screen and is meant for a trusted machine or network; set GOODSENTRY_AUTH=required to enable sign-in, then configure your public domain and database credentials before exposing the stack.

A CLEAR STATUS

Useful today.
Still being built.

GoodSentry is an independent Go implementation in active development. Full Sentry compatibility and GlitchTip feature parity are not complete.

Error tracking, performance and typed logs, uptime and alerting, people and team management, verified account emails, optional TOTP two-factor sign-in, instance-wide OIDC plus per-organization OpenID Connect sign-in applications with a shareable login page, Sentry-compatible management APIs, minidump and DWARF/dSYM symbolication, Grafana Sentry data source panels and an opt-in MCP server with OAuth PKCE are implemented and tested. Vendor-specific provider deployments and external identity-provider receipts, automatic repository synchronization, cold archival and the final requirement audit remain on the roadmap. OpenTelemetry log ingestion works through standard OTLP/HTTP exporters. Public amd64 and arm64 application images are available; a concurrent four-SDK workload measured 24.4 MiB of application memory with PostgreSQL excluded.
